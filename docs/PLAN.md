# แผนย้าย DriveGo จาก HTML เป็นระบบ Full Stack

บันทึกเมื่อ: 2026-10-14
ไฟล์ต้นฉบับ: `DRIVEGO_TRIAL_v23.html` (32,289 บรรทัด, ทุกอย่างอยู่ในไฟล์เดียว)
ข้อค้นพบและข้อตัดสินใจประกอบแผนนี้อยู่ใน [NOTES.md](NOTES.md)

## เป้าหมาย
1. **ฟังก์ชันไม่หลุด:** การทำงานของปุ่ม หน้าตา และลำดับขั้นตอนต้องเหมือน HTML เดิม (บทเรียนจากรอบ Next.js ที่หลุดทั้งสามเรื่อง)
2. **รองรับการเติบโต:** หลักร้อยอู่ในช่วงแรก และ 2,000–3,000 อู่ (4,000–15,000 user) ภายใน 5 ปี
3. **ดูแลต่อง่าย:** ระบบสุดท้ายเป็น Next.js + TypeScript ที่หาคนมาดูแลได้

## หลักการ
- **HTML เดิมคือเฉลย** ทุกอย่างที่ทำต้องผ่านการเทียบกับเฉลย ไม่ใช่ให้ AI หรือคนตัดสินด้วยสายตา
- **ไม่เขียนใหม่ทั้งหมดในครั้งเดียว** ย้ายทีละส่วน และระบบต้องใช้งานได้ทุกขั้น
- **ดูพฤติกรรมตอนโปรแกรมทำงานจริง ไม่ใช่อ่านโค้ด** เพราะฟังก์ชัน 204 ตัวถูกครอบหรือแทนที่ตอนโปรแกรมทำงาน จนโค้ดที่ทำงานจริงไม่ใช่โค้ดที่ประกาศไว้
  (วัดด้วย `npm run inventory` ดู [BEHAVIORS.md](BEHAVIORS.md))
  (ตัวอย่าง: `markPaid` ที่บรรทัด 8531 ถูกครอบที่บรรทัด 23536 ทำให้ทำงานต่างจากที่อ่านเจอ)
- **มีกรรมการ 3 ตัว:**

  | ปัญหา | กรรมการ | วิธีตรวจ |
  |---|---|---|
  | ปุ่มทำงานไม่เหมือน | เทียบข้อมูลก่อนและหลังกดปุ่ม | ส่วนต่างของ `DB` ต้องตรงกับ HTML เดิม (ไม่เทียบ ID สุ่มและเวลา) |
  | หน้าตาเพี้ยน | เทียบภาพหน้าจอ | ภาพจาก HTML เดิมเป็นเฉลย แล้วเทียบกับหน้าใหม่ |
  | ลำดับขั้นตอนเพี้ยน | อัดขั้นตอนแล้วเล่นซ้ำ | ทุกขั้นต้องเปิดหน้า popup และข้อความเดียวกับของเดิม |

- **คุณอนุมัติทุกเฟสผ่าน PR**

- ใส่ HTML ต้นฉบับไว้ใน `legacy/` และห้ามแก้
- เขียน `CLAUDE.md` เป็นกติกาให้ agent ทำตาม
- ตั้ง Playwright ให้ล็อกเวลาไว้คงที่ ใช้ข้อมูลตั้งต้นชุดเดียวกันทุกครั้ง และล็อกอินผ่าน `?login=account` (บัญชีทดสอบ `dg1688`)
  - ห้ามพึ่งข้อมูลทดลองที่ระบบสร้างเองตอนเปิด เพราะได้ผลไม่เท่ากันในแต่ละรอบ (ใบเสร็จ 14 หรือ 2,055 ใบ ขึ้นกับจังหวะการโหลด)
  - `seedDemo36()` ใช้ตัวสุ่มที่ล็อกค่าตั้งต้นไว้ ถ้าล็อกวันที่ด้วยจะได้ข้อมูลชุดเดิมทุกครั้ง จึงใช้เป็นข้อมูลชุดใหญ่สำหรับทดสอบรายงานได้
- เขียนสคริปต์สร้าง `behaviors.csv` รายการพฤติกรรมทั้งหมด: ฟังก์ชันระดับบนสุด 916 ตัว (บันทึกข้อมูล 196 ตัว),
  จุดรับคำสั่งที่เขียนใน HTML 639 จุด และตัวรับเหตุการณ์ที่ผูกด้วยโค้ด 522 จุด (ดู [BEHAVIORS.md](BEHAVIORS.md))
- ระบบบันทึกเฉลย 3 แบบ: ข้อมูลก่อนและหลังกดปุ่ม, ภาพหน้าจอ, การอัดขั้นตอน
- สถานการณ์เรื่องเงิน ภาษี และสต๊อก 20–30 เรื่อง **เจ้าของโปรเจกต์เป็นคนยืนยันผลที่ถูกต้อง**
  จะอัดเองด้วย `playwright codegen` หรือพิมพ์ขั้นตอนเป็นภาษาไทยให้ Claude แปลงเป็น test ก็ได้ ตัวอย่าง:

  - VAT, การตัดสต๊อกแบบ FIFO, รับชำระลูกหนี้, ซื้อสินค้าเข้าสต๊อก
  - เงินเดือนและประกันสังคม, สิทธิ์ของพนักงานแต่ละตำแหน่ง, เลขที่เอกสารต่อเนื่อง, สาขา
- วัด coverage ให้ฟังก์ชันที่บันทึกข้อมูลทั้ง 196 ตัวถูกเรียกอย่างน้อยหนึ่งครั้ง

**เสร็จเมื่อ:** รันเฉลยทั้งหมดกับ HTML เดิมซ้ำกี่รอบก็ได้ผลเหมือนเดิมทุกรอบ

**สถานะ (2026-10-15):** ระบบ test กรรมการ 3 ตัว รายการพฤติกรรม และสถานการณ์ 84 เรื่อง ครบทั้ง 3 แพ็กเกจ (Biz, ProX, Franchise) เสร็จแล้ว

### เฟส 1: แยกไฟล์ (ยังไม่มีหลังบ้าน)
- แยกไฟล์เดียวเป็น `index.html`, `css/`, `js/` (เรียงตามลำดับ script เดิม), `assets/` (รูปที่ฝังแบบ base64) ห้ามแก้ logic หรือข้อความ

**เสร็จเมื่อ:** เฉลยผ่านทั้งหมด และภาพหน้าจอตรงกับต้นฉบับทุกพิกเซล

### เฟส 2: หลังบ้านและฐานข้อมูล (หน้าบ้านยังเป็นโค้ดเดิม)
- สร้างแอป Next.js + PostgreSQL และเสิร์ฟหน้าบ้านเดิมจากแอปนี้
- เปลี่ยน `STORE.get/set` และ `save()` ให้ส่งไป server **เฉพาะรายการที่เปลี่ยน** แทนการส่งทั้งก้อน 15–18 MB
- เริ่มด้วยตารางแบบทั่วไป: `id, shop_id, branch_id, data (JSONB), updated_at, version`
- ย้ายล็อกอินไปที่ server เก็บรหัสผ่านแบบ hash (bcrypt หรือ argon2) และไม่ส่งรหัสผ่านไปที่เบราว์เซอร์
- ให้ `shop_id` มาจาก session ฝั่ง server เปิด Row-Level Security และส่งค่าด้วย `SET LOCAL` (รายละเอียดใน NOTES.md)

**เสร็จเมื่อ:** เฉลยทั้งหมดผ่านบนระบบใหม่ และ test ยืนยันว่าอู่ A เห็นข้อมูลอู่ B ไม่ได้

### เฟส 3: ย้าย logic สำคัญไปทำที่ server (ทีละฟังก์ชัน, 1 PR ต่อเรื่อง)
- ออกเลขที่เอกสาร (`DB.seq`) ใน transaction เพื่อกันเลขใบกำกับภาษีซ้ำ
- สิทธิ์การใช้งาน, การตัดสต๊อกแบบ FIFO, การคำนวณ VAT / หัก ณ ที่จ่าย / ประกันสังคม, audit log
- เปลี่ยน ProX จากการดึงข้อมูลทุก 7 วินาทีเป็นให้ server ส่งมาเองด้วย SSE หรือ WebSocket (รายละเอียดใน NOTES.md)
- ย้ายไฟล์แนบ (ตอนนี้เป็น data URL ใน `DB.px.learn`) ไปเก็บใน object storage

**เสร็จเมื่อ:** ข้อมูลก่อนและหลังกดปุ่มตรงกับเฉลย และแก้ข้อมูลสำคัญจากเบราว์เซอร์ไม่ได้
จากนั้น**เปิดใช้จริงกับอู่นำร่อง**ได้

### เฟส 4: ย้ายหน้าจอไป React ทีละหน้า
- เริ่มจากหน้าที่ข้อมูลเยอะ: รายการใบเสร็จ, รายงาน, หน้าแรก
- ใช้การแบ่งหน้า (pagination) และให้ฐานข้อมูลเป็นคนสรุปยอด จะได้ไม่ต้องโหลดข้อมูลทั้งก้อนทุกครั้งที่เข้าระบบ
- ทยอยเปลี่ยนช่องข้อมูลใน JSONB ให้เป็นคอลัมน์จริงตามหน้าที่ย้าย
- ลบหน้าเก่าได้เมื่อหน้าใหม่ผ่านกรรมการครบทั้ง 3 ตัว

**เสร็จเมื่อ:** ไม่เหลือหน้าจอจาก HTML เดิม

### เฟส 5: ขยายรองรับ (ทำต่อเนื่องตามการเติบโต)
- ทดสอบรับโหลดด้วย k6 ก่อนเปิดใช้งาน และเมื่อถึง 500, 1,000 และ 3,000 อู่
- ระบบเฝ้าดูระบบ, แจ้งเตือน error, สำรองข้อมูลพร้อมซ้อมกู้คืน, ระบบ deploy อัตโนมัติ
- เพิ่ม Redis, งานเบื้องหลัง และฐานข้อมูลสำรองไว้อ่าน (read replica) เมื่อตัวเลขบอกว่าจำเป็น

## โครงสร้างระบบปลายทาง

| ส่วน | ใช้อะไร |
|---|---|
| หน้าบ้าน + API | Next.js + TypeScript แอปเดียว โดยแยกโค้ดธุรกิจไว้ในโฟลเดอร์ของตัวเอง ถ้าวันหน้าต้องแยก API ออกไปก็ทำได้ง่าย |
| ฐานข้อมูล | PostgreSQL แบบ managed ใช้ `shop_id` + `branch_id` และ Row-Level Security |
| ไฟล์แนบ | object storage |
| การรัน | server หรือ container ที่ทำงานตลอดเวลา (ไม่ใช่ serverless ล้วน) เพราะต้องรักษาการเชื่อมต่อ SSE/WebSocket |
| ขนาดเริ่มต้น | API 1 เครื่อง (เพิ่มเป็น 2–3 เครื่องใน 5 ปี) + PostgreSQL 1 ตัว ยังไม่ต้องใช้ microservices หรือ Kubernetes |

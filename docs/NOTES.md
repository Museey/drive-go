# บันทึกโปรเจกต์ DriveGo

บันทึกข้อค้นพบและข้อตัดสินใจระหว่างวางแผนย้ายจากไฟล์ HTML เดียวไปเป็นระบบ full stack
เลขบรรทัดที่อ้างถึงทั้งหมดอ้างอิงไฟล์ต้นฉบับ `DRIVEGO_TRIAL_v23.html`

## ขนาดระบบที่คาดไว้

บันทึกเมื่อ: 2026-10-14 (ตัวเลขจำนวนอู่และ user มาจากเจ้าของโปรเจกต์)

| | ช่วงแรก | 5 ปี |
|---|---|---|
| จำนวนอู่ | หลักร้อย | 2,000–3,000 |
| user ต่ออู่ | 2–3 (มากสุด 5) | 2–3 (มากสุด 5) |
| user รวม | ประมาณ 300–1,500 | ประมาณ 4,000–15,000 |
| server ที่น่าจะพอ | API 1 เครื่อง + PostgreSQL แบบ managed | API 2–3 เครื่อง + PostgreSQL ที่ใหญ่ขึ้น (เพิ่ม read replica ถ้ารายงานหนัก) |
| ปริมาณข้อมูล | ไม่กี่ GB | ประมาณ 15–18 GB ต่อปี รวม 5 ปีหลักสิบ GB |

ที่มาของปริมาณข้อมูล: วัดจากข้อมูลทดสอบ 36 เดือน (`seedDemo36()`) ซึ่งเป็นอู่ยอดขาย 2–5 ล้านบาทต่อเดือน
ได้ 15–18 MB ต่ออู่ (ในรูป JSON) หรือประมาณ 5–6 MB ต่ออู่ต่อปี อู่จริงส่วนใหญ่น่าจะเล็กกว่านี้
ส่วนที่ใหญ่ที่สุดคือ `fifo` 4.7 MB, `receipts` 3.7 MB (2,055 ใบ), `quotes` 3.5 MB และ `stockCuts` 3.3 MB

สรุป:
- ระบบนี้เป็นขนาดกลาง PostgreSQL ตัวเดียวรองรับได้ ยังไม่ต้องใช้ microservices หรือ Kubernetes
- ไฟล์เดิมบันทึกข้อมูลทั้งก้อนทุกครั้งที่เรียก `save()` ก่อนย้ายขึ้น server ต้องเปลี่ยนเป็นบันทึกเฉพาะรายการที่เปลี่ยน
  ไม่อย่างนั้นทุกการบันทึกจะส่งข้อมูล 15–18 MB และคนที่บันทึกทีหลังจะเขียนทับข้อมูลของคนอื่น
- ทดสอบรับโหลด (เช่นด้วย k6) เมื่อถึง 500, 1,000 และ 3,000 อู่ แทนการออกแบบเผื่อ 5 ปีตั้งแต่วันแรก

## การแยกข้อมูลแต่ละอู่ด้วย `shop_id`

บันทึกเมื่อ: 2026-10-14

### ข้อตัดสินใจ
ทุกอู่ใช้ฐานข้อมูล PostgreSQL ชุดเดียวกัน แยกข้อมูลของแต่ละอู่ด้วยคอลัมน์ `shop_id`
ไม่แยกฐานข้อมูลอู่ละก้อน เพราะ 2,000–3,000 ฐานข้อมูลต้อง migrate และ backup ทีละก้อน ดูแลยากมาก

### กติกา
- ทุกตารางที่เป็นข้อมูลของอู่ต้องมี `shop_id` ข้อมูลระดับสาขาต้องมี `branch_id` ด้วย
- index ขึ้นต้นด้วย `shop_id` เช่น `(shop_id, date)`
- `shop_id` ต้องมาจาก session ฝั่ง server เท่านั้น ห้ามใช้ค่าที่ browser ส่งมา
- เครือ Franchise นับเป็น 1 `shop_id` และแยกสาขาด้วย `branch_id` ตามพฤติกรรมของไฟล์เดิมที่ให้ HQ เห็นทุกสาขาในเครือ

### ความเสี่ยงและวิธีป้องกัน
ความเสี่ยง: ถ้าโค้ดจุดไหนลืมกรอง `shop_id` อู่หนึ่งจะเห็นหรือแก้ข้อมูลของอีกอู่ได้

- เปิด Row-Level Security ของ PostgreSQL เป็นด่านสุดท้าย ให้ฐานข้อมูลกรองเองตาม `shop_id` ของ request นั้น แม้โค้ดจะลืมกรอง
- ส่ง `shop_id` ให้ฐานข้อมูลด้วย `SET LOCAL` ภายใน transaction เพื่อไม่ให้ค่าค้างข้าม connection เมื่อใช้ connection pool
- ต้องมี test ใน CI ที่ล็อกอินเป็นอู่ A แล้วยืนยันว่าทุก API อ่านหรือแก้ข้อมูลของอู่ B ไม่ได้เลย

## ProX ดึงข้อมูลจาก server ถี่เกินไป (polling)

บันทึกเมื่อ: 2026-10-14

### ปัญหา
โหมดออนไลน์ของ ProX ดึงข้อมูลจาก server ประมาณ **3 ครั้งทุก 7 วินาทีต่อ user**
ถ้ามี 1,000 คนออนไลน์ จะเป็นประมาณ **430 request ต่อวินาที** จากการดึงข้อมูลอย่างเดียว
ทั้งที่ส่วนใหญ่ไม่มีอะไรเปลี่ยน

ที่มา: บรรทัด 19117 ในฟังก์ชัน `pxNetToggle()` เมื่อกด "เชื่อมต่อสาขา" จะตั้ง `setInterval(..., 7000)` ที่เรียก:

| ฟังก์ชัน | request | ความถี่ |
|---|---|---|
| `pxNetPull()` | `GET /api/queue` | ทุก 7 วินาที |
| `dcPull()` | `GET /api/dc/products` และ `GET /api/dc/requests` | ทุก 7 วินาที (2 request) |
| `pxStockReport(false)` | `POST /api/stock/report` | ประมาณทุก 55 วินาที (เฉพาะบัญชีสาขา) |

`/api/dc/products` ส่งรายการสินค้าทั้งหมดกลับมาทุกครั้ง จึงหนักทั้งจำนวน request และขนาดข้อมูล

### ประมาณการตามขนาดที่คาดไว้
ใช้ตัวเลขจากหัวข้อ "ขนาดระบบที่คาดไว้" ข้างบน
ระบบหลังบ้านมักเปิดหน้าจอค้างไว้ทั้งวัน ตัวเลขด้านล่างจึงคิดจากกรณีสูงสุดที่ทุกคนเปิดโหมดออนไลน์พร้อมกัน

| ระยะ | อู่ | user | request ต่อวินาทีจาก polling |
|---|---|---|---|
| ช่วงแรก | ~300 | ~900 | ~390 |
| 5 ปี | ~2,500 | ~7,500 | ~3,200 |

### แนวทางแก้
- เปลี่ยนเป็นให้ server ส่งข้อมูลมาเองเมื่อมีอะไรเปลี่ยน (WebSocket หรือ SSE) เช่น มีคิวจองใหม่ หรือคำขอเบิกจาก DC เปลี่ยนสถานะ
- รายการสินค้า DC: โหลดครั้งเดียวตอนเชื่อมต่อ หลังจากนั้นรับเฉพาะรายการที่เปลี่ยน
- รายงานสต๊อก: ส่งเมื่อสต๊อกเปลี่ยนจริง แทนการส่งตามเวลา
- ต้องรันบน server หรือ container ที่ทำงานตลอดเวลา (ไม่ใช่ serverless ล้วน) เพราะต้องรักษาการเชื่อมต่อค้างไว้
- ทางบรรเทาชั่วคราวระหว่างยังไม่แก้: หยุด polling เมื่อแท็บไม่ได้เปิดดูอยู่ (Page Visibility API)

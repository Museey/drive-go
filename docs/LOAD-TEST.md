# ทดสอบรับโหลด (k6)

LAUNCH-CHECKLIST ด่าน 1 "ทดสอบรับโหลดขนาดอู่นำร่อง (หลายเครื่องในอู่บันทึกพร้อมกัน) ด้วย k6"
และ NOTES.md "ทดสอบรับโหลดเมื่อถึง 500, 1,000 และ 3,000 อู่" ใช้เครื่องมือชุดนี้

## แต่ละเครื่องทำอะไร

สิ่งที่เครื่องหนึ่งส่งถึง server อัดมาจากหน้าจอจริง (`tools/load/capture.mjs`) ไม่ได้เขียนขึ้นเอง k6 จึงส่งแบบเดียวกับเบราว์เซอร์:

1. **เปิดโปรแกรมและเข้าระบบ:** คำขอทุกตัวตามลำดับ (19 ตัว) ได้แก่
   - อ่านข้อมูลร้านทั้งก้อน: ร้าน 36 เดือน `garage.v22` ราว 14 MB
   - ตรวจรหัสผ่านซ้ำ บันทึกว่าใครเข้า
   - สำรองข้อมูลประจำวัน: แต่ละเครื่องทำวันละครั้ง
2. **เปิดช่องรับการอัปเดตสด** (`/api/live`) ค้างไว้จนจบ เหมือนเบราว์เซอร์
3. **ทำงานซ่อมทีละงานจนหมดเวลา** งานละ 3 บันทึก:
   - สร้างใบเสนอราคา (ลูกค้าจริงของร้าน อะไหล่ 1 รายการ ค่าแรง 1 รายการ)
   - อนุมัติ
   - ตัดสต็อกและรับเงินสดเต็มจำนวน ("ปิดการขาย": สต็อก FIFO การเคลื่อนไหว เลขที่เอกสาร)

   ทุกครั้ง:
   - ใช้รหัสรายการใหม่และเลขที่เอกสารถัดไป
   - อ่านแถวที่จะแก้ก่อน (เหมือนเครื่องที่ได้ยินการอัปเดตสดแล้ว)
   - ถ้าชนกับเครื่องอื่น (409) จะอ่านข้อมูลใหม่ทั้งก้อนแล้วบันทึกอีก ไม่เกิน 3 ครั้ง เหมือนคนทำซ้ำหลังโปรแกรมโหลดใหม่
4. **หลังทุกบันทึก** เครื่องอื่นในร้านเดียวกัน (เครื่อง − 1) ขอแถวที่เปลี่ยน เหมือนตอนได้ยินจากการอัปเดตสด

งานแรกของร้านอาจเพิ่มช่องข้อมูลที่ข้อมูลเก่ายังไม่มี ตัวอัดจึงทำ 2 งานแล้วใช้งานที่สอง และเปิดทุกร้านผ่านหน้าจอก่อนหนึ่งครั้ง
(ร้านที่ข้อมูลเก่ากว่า FIFO จะย้ายสต็อกเข้า FIFO ตอนเปิดครั้งแรก) สองอย่างนี้จึงไม่อยู่ในตัวเลข

## ค่าตั้งต้นและเกณฑ์ผ่าน

| ค่า | ตั้งต้น | หมายถึง |
|---|---|---|
| `--shops` | 3 | อู่นำร่อง 3 อู่ |
| `--devices` | 5 | เครื่องต่ออู่ (เคาน์เตอร์ เจ้าของ ช่าง) |
| `--dataset` | `biz-full` | ข้อมูล 36 เดือนของระบบเดิม (อู่ที่ใช้มา 3 ปี) สร้างเองถ้ายังไม่มี (`npm run fixture -- biz full` ไม่เก็บใน git) |
| `--ramp` | 10 | ทุกเครื่องเปิดโปรแกรมภายใน 10 วินาที (ตอนเช้า) |
| `--minutes` | 5 | เวลาทำงานหลังเปิด |
| `--think` | 5-15 | วินาทีระหว่างสองบันทึกของเครื่องเดียว (ของจริงเป็นนาที: เร็วกว่าจริงราว 10 เท่า) |
| `--cpus` | 1 | server ในเครื่องนี้ใช้ได้ 1 CPU เท่า server ทดสอบ (`apps-s-1vcpu-1gb`) |
| `--memory-mb` | 1024 | หน่วยความจำของ server ทดสอบ |

ไม่ผ่านถ้า (k6 thresholds ใน `tools/load/pilot.js`):
- เข้าระบบ p95 ≥ 1.5 วินาที
- อ่านข้อมูลทั้งก้อน p95 ≥ 8 วินาที
- บันทึก p95 ≥ 1 วินาที
- ขอแถว p95 ≥ 0.5 วินาที
- บันทึกสำเร็จต่ำกว่า 99%
- มีคำตอบผิดปกติแม้แต่ครั้งเดียว
- หน่วยความจำสูงสุดของ server เกิน 85% (ตัวรันวัดเอง เฉพาะการรันในเครื่องนี้)

## วิธีรัน

```bash
npm run load                          # ในเครื่องนี้ ต้องมี k6 (https://grafana.com/docs/k6/latest/set-up/install-k6/)
npm run load -- --node                # ไม่มี k6: tools/load/k6-node รันสคริปต์เดียวกัน (ตรวจว่าสคริปต์ใช้ได้ ตัวเลขจริงใช้ของ k6)
npm run load -- --shops 1 --devices 10 --minutes 10
LOAD_USER=… LOAD_PASS=… npm run load -- --url https://<แอป> --shop load-1,load-2   # server ทดสอบ
```

**k6 ตัวจริงบน GitHub (เจ้าของโปรเจกต์เลือก 2026-10-31):**
- workflow "Load test (k6)" (`.github/workflows/load-test.yml`) กดรันเองที่ Actions → Load test (k6) → Run workflow
  - ติดตั้ง k6 ด้วย action ของ Grafana (`grafana/setup-k6-action`)
  - รัน `npm run load` บนเครื่องของ GitHub: server ใช้ 1 CPU และข้อมูล 36 เดือนสร้างเองในเครื่องนั้น
- ใส่ URL ของ server ทดสอบและรหัสร้านที่เปิดไว้ทดสอบ เพื่อยิง server จริง
  - ต้องตั้ง secret `LOAD_USER` และ `LOAD_PASS` ของ repository ก่อน (ใส่ที่ GitHub เท่านั้น ห้ามส่งในแชต)
- ผลอยู่ในหน้าสรุปของการรัน และใน artifact `load-results`

**กับ server ทดสอบ:**
- ใช้เฉพาะร้านที่ทีมงานเปิดไว้ทดสอบ ห้ามใช้ร้านจริง เพราะการทดสอบเพิ่มเอกสารลงร้าน
- ร้านต้องมีลูกค้าที่มีรถและอะไหล่ที่มีสต็อก 5 ชิ้นขึ้นไป
- ตัวอัดใช้ได้ทั้งข้อมูลแบบร้านทดลอง ("พร้อมทดลอง" ปิดการขายแล้วได้ใบเสร็จ MA-RE ทันที)
  และข้อมูล 36 เดือน (ปิดการขายแล้วขึ้นการ์ด "บันทึกข้อมูลสำเร็จ")
- ดูหน่วยความจำและ CPU ที่ Insights ของแอปใน DigitalOcean (ตัวรันวัดได้เฉพาะในเครื่องนี้)

ไฟล์ผล (โฟลเดอร์ที่ตัวรันบอกตอนจบ หรือ `--out`):
- `capture.json`: สิ่งที่อัดได้ ไม่มีรหัสผ่าน
- `summary.json`: ผลของ k6
- `report.json`: ค่าตั้ง และหน่วยความจำทุกวินาที

ตัวเลขสูงสุดของการบันทึกและการขอแถว (~2 วินาที) เกิดตอนที่เครื่องอื่นกำลังเปิดโปรแกรม

**ข้อค้นพบ**

1. **ช่วงทำงานระหว่างวันรับได้สบาย** บันทึกเร็วแม้เร็วกว่าจริงราว 10 เท่า

2. **ช่วงเปิดโปรแกรมพร้อมกันตอนเช้าคือคอขวด**
   - ราคาหน่วยความจำ (วัดแยกด้วยสคริปต์ชั่วคราว):
     - เปิดโปรแกรมหนึ่งเครื่องอ่านข้อมูลทั้งก้อน (+80–100 MB ชั่วคราว) และสำรองข้อมูลทั้งก้อน (+100 MB)
     - 5 เครื่องพร้อมกัน +300 MB
     - หลังจากนั้น Node ไม่คืนหน่วยความจำให้ระบบทันที (ค้างที่ ~820 MB)
   - บน server 1 GB ที่ DigitalOcean ถ้าเกินขีดแอปจะถูกปิดแล้วเริ่มใหม่ (alert `RESTART_COUNT`)
   - ร้านใหม่ช่วงนำร่องข้อมูลน้อยกว่านี้มาก แต่ร้านที่ใช้มา 1–3 ปีจะถึงจุดนี้

3. **ระหว่างสำรองข้อมูล server หยุดตอบคำขออื่น** การบีบอัดไฟล์สำรอง (`gzipSync`) ทำในตัว server แบบรอให้เสร็จ (ข้อมูล 14 MB)

**เจ้าของโปรเจกต์ตัดสิน 2026-10-31: แก้โปรแกรม (ไม่เพิ่มขนาด server) และรัน k6 จริงบน GitHub Actions** แก้แล้ว:
- ก. **คิวงานหนัก** (`server/lib/heavy.ts`):
  - อ่านข้อมูลหลักทั้งก้อน อ่านจุดสำรอง และทำจุดสำรอง พร้อมกันได้ไม่เกิน 2 งานต่อ server (`HEAVY_AT_ONCE`) งานอื่นรอตามลำดับ
  - เข้าคิวก่อนจองการเชื่อมต่อฐานข้อมูล งานที่รอจึงไม่กันการบันทึกของคนอื่น
- ข. **ไม่ทำจุดสำรองของวันซ้ำเมื่อข้อมูลไม่เปลี่ยน** (`makeBackup`):
  - แผนเดิม "วันละครั้งต่อร้าน" ใช้ไม่ได้ เพราะปุ่ม "สร้างจุดสำรองเดี๋ยวนี้" ใช้คำขอเดียวกัน และต้องได้ข้อมูล ณ ตอนกด
  - ทำแทนว่า ถ้าไม่มีการบันทึกหรือแถวใดเปลี่ยนตั้งแต่จุดสำรองของวันนั้น (เผื่อ 1 นาทีให้การบันทึกที่กำลังเสร็จ) ก็ไม่ทำใหม่
  - ผลเหมือนทำใหม่ทุกครั้ง แต่ตอนเช้าที่ยังไม่มีใครบันทึก เครื่องที่เปิดตามมาไม่ต้องทำซ้ำ
- ค. **บีบอัดและคลายจุดสำรองนอกเส้นทางหลักของ server** (zlib แบบ async) ไม่หยุดคำขออื่นระหว่างบีบอัด 14 MB

# ตรวจช่องโหว่และสิ่งที่ควรปรับปรุง (2026-11-23)

เจ้าของโปรเจกต์ขอ (2026-11-23) "ตอนนี้เริ่มมีอู่ทดลองใช้และอู่นำร่องแล้ว อยากให้ช่วยหาช่องโหว่ของระบบเรา หรือมีอะไรที่ควรพัฒนา ปรับปรุง แก้ไข"
ตรวจ 4 ด้านพร้อมกัน (agent 4 ชุด) **อ่านโค้ดและลองกับ server ชั่วคราวในเครื่องของ session เท่านั้น ไม่ได้ส่งคำขอใดไปที่ app.drivegox.com**
สคริปต์ที่ใช้ลองอยู่ใน scratchpad ของ session (หายได้) เอกสารนี้จึงจดที่ตั้งในโค้ดและวิธีแก้ไว้ ไม่จดตัวโจมตีทีละขั้น

ระดับ: **ร้ายแรงมาก** = คนนอกที่ไม่ได้เข้าระบบทำได้ หรือข้อมูลทุกร้านเสี่ยง · **สูง** = คนในร้าน (พนักงาน/สาขา) ทำได้ หรือเสียข้อมูลได้ · **กลาง** · **ต่ำ**
"ยืนยันแล้ว" = ลองแล้วเกิดจริงบน server ชั่วคราว

## ก. ด่วน (ทำทันที)

1. **ร้ายแรงมาก · คนนอกทำ server ล่มได้ (ยืนยันแล้ว)** `server/app/api/storage/[key]/route.ts` POST/PUT อ่านและแปลงข้อมูลที่ส่งมาสูงสุด 30 MB
   ก่อนตรวจว่าเข้าระบบ (GET เข้าคิวงานหนักก่อนตรวจ) คำขอแบบไม่บอกขนาด (chunked) ข้ามคิวงานหนัก คิวไม่มีเวลาหมด
   คำขอไม่มี cookie 2–3 คำขอพร้อมกันพอให้เครื่อง 512 MB หน่วยความจำเต็มแล้วเริ่มใหม่ (ทุกร้านหลุด) และคำขอส่งช้า ๆ 1 คำขอทำให้ร้านอื่นเปิดโปรแกรมช้าเป็นนาที
   แก้: ตรวจ session (และบังคับ Content-Length) ก่อนอ่านข้อมูล ใส่เวลาหมดให้คิวงานหนักและหยุดเมื่อคำขอถูกยกเลิก
2. **ร้ายแรงมาก · ฐานข้อมูลเต็มได้ ทุกร้านอ่านอย่างเดียว (กลไกยืนยันแล้ว)** ข้อผิดพลาด 500 ทุกครั้งถูกบันทึกลงตาราง errors โดยไม่จำกัด
   (คำขอว่างที่ไม่ได้เข้าระบบก็ทำให้เกิด 500 ได้: ลองแล้ว 10 วินาที 5,495 แถว) และงานทุกชั่วโมงแจ้งเตือนทุกครั้ง ·
   ผู้ที่เข้าระบบได้ PUT ข้อมูลชื่อใดก็ได้ ครั้งละ 29 MB ไม่มีโควตา (`storage.ts writeBlob`) ไฟล์ "หลักฐาน" ข้ามโควตา (`files.ts:77`) ·
   ไฟล์แนบ จุดสำรอง และประวัติ 5 ปี อยู่ในฐานข้อมูล 10 GB ก้อนเดียวกัน ไม่มีแจ้งเตือนพื้นที่ฐานข้อมูล
   แก้: จำกัดอัตราการบันทึกข้อผิดพลาดของ server, รับเฉพาะชื่อข้อมูลที่รู้จักพร้อมจำกัดขนาด, นับไฟล์หลักฐานในโควตา, ตั้งแจ้งเตือนพื้นที่ฐานข้อมูล 70%
3. **สูง · ร้านตัวอย่างรหัสผ่านสาธารณะอยู่บน server เดียวกับอู่จริง** `SEED_DEMO_SHOPS=1` (`.do/app.yaml:87`) รหัสอยู่ในคู่มือและ `05.js`
   ใครก็เข้า demo-biz ได้ แล้วทำข้อ 2, เปิดช่องอัปเดตสดไม่จำกัด (2,000 ช่องจาก session เดียว = หน่วยความจำเต็ม) หรือยึดคิวงานหนัก
   (รายการใน LAUNCH-CHECKLIST "ก่อนเปิดอู่นำร่องบน server เดียวกับ server ทดสอบ" ยังไม่ได้ขีด) แก้: ปิดร้านตัวอย่างบน server นี้ (หรือแยก server สาธิต) และจำกัดช่องอัปเดตสดต่อ session
4. **สูง · พนักงานที่ไม่มีสิทธิ์ทำลายหรือปลอมข้อมูลทั้งร้านได้ (ยืนยันแล้ว)**
   - บันทึกที่เปลี่ยนโครงสร้างข้อมูล (`changes.layout`, แถว `DB.`) ผ่าน (`permissions.ts:109`, `storage.ts:118`, `units.ts:182`): ร้านเปิดไม่ได้อีก หรือทุกคนเห็นข้อมูลที่พนักงานเขียนเอง
   - ล้างข้อมูลทั้งร้าน (`whole`) และเขียนทับจุดสำรอง (PUT `.bak.`) ได้ (`route.ts:109,133`) ประวัติการใช้งานลบทีเดียวได้ (ไม่นับใน mass removal)
   - ฝังจุดสำรองที่เมื่อเจ้าของกดกู้คืน พนักงานได้สิทธิ์ทุกอย่าง (`route.ts:119,153` เก็บ session fields ดิบลงจุดสำรอง)
   แก้: ไม่รับ layout/`DB.` จากผู้ที่ไม่ใช่ผู้จัดการ ตรวจ layout ทุกครั้ง, whole และ PUT จุดสำรองเฉพาะเจ้าของ/HB, รับ session fields เฉพาะที่รู้จักและเป็น JSON, ไม่ใช้ session fields ในจุดสำรอง, นับ DB.audit
5. **สูง · พนักงานฝังโค้ดให้รันในเบราว์เซอร์ของเจ้าของได้ (XSS, ยืนยันแล้ว)** server รับข้อความใดก็ได้ในช่องอื่นนอกจากบัญชีพนักงาน
   แล้วหน้าจอนำบางช่องไปแสดงโดยไม่ escape: `03.js:2758` (สถานะใบเสนอราคาใน select), `03.js:1206,1360,1528,1558,1574` (รูปสินค้า),
   `03.js:7626` (ประเภทรายการทุน), id ของรายการในปุ่ม onclick ราว 150 จุด · ลองแล้ว: เจ้าของเข้าระบบ โค้ดรันทันทีและอ่านเงินเดือนกับเลขบัตรประชาชนทุกคนได้
   CSP ของหน้าร้าน (`'unsafe-inline' 'unsafe-eval'` ไม่มี connect-src) ไม่กันเลยและส่งข้อมูลออกไปที่ไหนก็ได้
   รวมกับข้อ ข1 (เปลี่ยนรหัสผ่านไม่ต้องใส่รหัสเดิม) = พนักงานยึดบัญชีเจ้าของได้
   แก้: escape ทุกจุด (รวม id) ตรวจรูปแบบ id/สถานะ/ประเภทที่ server, เพิ่ม `default-src 'self'; connect-src 'self'; img-src 'self' data: blob:` ใน CSP
6. **สูง · สำรองข้อมูลมีที่เดียว และยังไม่เคยซ้อมกู้คืน** สำรองของ DigitalOcean 7 วัน บัญชีเดียวกัน ภูมิภาคเดียวกัน จุดสำรองของแอปอยู่ในฐานข้อมูลเดียวกัน
   บัญชีถูกระงับหรือกดลบผิด = ข้อมูลทุกร้านหาย (เอกสารบัญชีต้องเก็บ 5 ปี) · RESTORE-DRILL.md ยัง "ยังไม่ได้ซ้อม" และขั้นที่ 10 ไม่ได้เปลี่ยน STAFF_DATABASE_URL
   ขั้นที่ 15 ลบฐานเดิมพร้อมสำรอง · แก้: สำรองแบบเข้ารหัสทุกคืนไปเก็บนอก DigitalOcean 35 วันขึ้นไป แก้คู่มือ แล้วซ้อมจริง
7. **สูง · ทุก push ที่ CI ผ่านขึ้น server ที่อู่ใช้งานทันที** (`ci.yml` ขยับ deploy/test, `deploy_on_push`) รวม migration ทุกเวลา ไม่มีคนกด
   หลาย session push branch เดียวกัน · แก้: แยก server ใช้จริง หรือ branch ที่คนเลื่อนเอง และช่วงเวลา deploy

## ข. สำคัญ (1–2 สัปดาห์)

1. **สูง · เปลี่ยนรหัสผ่านไม่ต้องใส่รหัสเดิม (ยืนยันแล้ว)** ใครถือ session (เครื่องในอู่ที่เข้าระบบค้าง 30 วัน, XSS) เปลี่ยนรหัสเจ้าของได้ และ session ของเจ้าของตัวจริงถูกตัด
   (`route.ts:94-128`) แก้: server ต้องให้ใส่รหัสเดิมเมื่อเปลี่ยนรหัสของตัวเอง (หน้าจอต้องมีช่องรหัสเดิม = ข้อความใหม่ ต้องอนุมัติ)
2. **สูง · Franchise: พนักงานสาขา (SHB) ทำตัวเองเป็นเท่าเจ้าของได้ (ยืนยันแล้ว)** แก้ `empId` ของบัญชีตัวเอง (`permissions.ts:122`) แล้วเห็นเงินเดือนทั้งหมด ปิด/เปิดงวดภาษีได้
   · หัวหน้าสาขาเปลี่ยนชื่อผู้ใช้ตัวเองเป็น `hq` แล้วยึดการเข้าระบบของ HQ ได้ (ยืนยันแล้ว) · หัวหน้าสาขาอ่าน/ลบสำเนาของสาขาอื่น (`storage.ts:354`)
   · สาขาฝังโค้ดให้รันในเบราว์เซอร์ HQ ได้ทางใบขอเบิก (`04.js:834-875`) แก้: ให้เฉพาะ HQ/HB เปลี่ยน user/empId/ลำดับ, ชื่อผู้ใช้ไม่ซ้ำที่ server, escape
3. **กลาง · `/api/auth/check` ใช้ลองรหัสของบัญชีอื่นได้ (ยืนยันแล้ว)** พนักงานลองรหัสเจ้าของ สาขาลองรหัส HQ ไม่ถูกนับและไม่ลงประวัติ ลองผิด 5 ครั้งล็อกเจ้าของได้
   แก้: ตรวจได้เฉพาะบัญชีของตัวเอง (หรือผู้จัดการตรวจ PIN ของพนักงานตัวเองตามที่หน้าจอต้องใช้)
4. **กลาง · การล็อกหลังกรอกผิด 5 ครั้งถูกแข่งเวลาได้ (ยืนยันแล้ว: 60 คำขอพร้อมกันได้ลอง 38 ครั้ง)** PIN ของพนักงาน Franchise ไม่กำหนดความยาว
   และชื่อผู้ใช้ของเจ้าของ = รหัสร้าน (อยู่ใน URL) ใครก็ล็อกเจ้าของไว้ได้ตลอด แก้: จองครั้งที่ลองแบบ atomic, PIN 6 หลักขึ้นไป, ล็อกตามบัญชี+ที่อยู่ หรือหน่วงเวลาแทนล็อก
5. **กลาง · "ต้องเปลี่ยนรหัสผ่านครั้งแรก" บังคับแค่ที่เบราว์เซอร์ (ยืนยันแล้ว)** session จากรหัสชั่วคราวใช้ API ได้ทุกอย่าง กดโหลดหน้าใหม่ก็ข้ามหน้าต่างได้
   แก้: server ปฏิเสธทุกอย่างยกเว้นการตั้งรหัสใหม่และออกจากระบบ ขณะ `must_change`
6. **กลาง · ย้ายสาขาหรือลดตำแหน่งแล้ว session เดิมยังใช้สิทธิ์เดิม 30 วัน (ยืนยันแล้ว)** แก้: จบ session ที่ขอบเขตหรือบทบาทไม่ตรงบัญชีแล้ว
7. **กลาง · สิทธิ์ส่วนใหญ่บังคับแค่ที่หน้าจอ (ยืนยันแล้ว)** พนักงานไม่มีสิทธิ์ แก้ราคาขาย ราคาในใบเสร็จ ลบใบขาย/ใบเสร็จ/ลูกค้า แก้ช่วงเวลายกเลิกเอกสาร ผ่าน API ได้
   ProX: การจำกัดสาขาของพนักงานอยู่ที่หน้าจอ แก้: เพิ่มการตรวจที่ server สำหรับการลบเอกสารและข้อมูลหลัก ราคา และ cancelWindow
8. **กลาง · PDPA: ประวัติลา (มีหมายเหตุอาการป่วย) และใบเตือนของทุกคน พนักงานทุกคนอ่านได้** (`visibility.ts:57`) แก้: ซ่อนเว้นผู้มีสิทธิ์งานบุคคล/เจ้าของ เห็นของตัวเอง
9. **กลาง · แอปร้านถือรหัสฐานข้อมูลของหน้าทีมงาน (`drivego_staff`)** ซึ่งอ่าน/เขียนได้ทุกร้าน บั๊กฝั่ง server ข้อเดียวกลายเป็นข้ามร้าน แก้: แยก /ops เป็นแอปของตัวเอง หรือใช้ฟังก์ชัน SECURITY DEFINER เฉพาะงาน
10. **กลาง · ความจุและจุดล้มจุดเดียว** web ยัง 512 MB (LOAD-TEST และ checklist บอก 1 GB ก่อนมีอู่นำร่อง), `HEAVY_AT_ONCE=1` ทุกร้านรอคิวเดียว,
    web 1 เครื่อง ฐานข้อมูล 1 node, ยังไม่ได้ตัดสินว่าระบบหยุดได้นานเท่าไร · pool ไม่มีเวลาหมดของ connection/คำสั่ง
11. **กลาง · การแจ้งเตือน** งานทุกคืนจบด้วย 3 ทุกคืนที่มีร้านรอโทร และใครก็ทำให้งานทุกชั่วโมงแจ้งเตือนได้ (ข้อ ก2) แจ้งเตือนจริงจะจมหาย ·
    แจ้งเตือนไปอีเมลบัญชี DO อย่างเดียว ยังไม่ยืนยันว่ามาถึง · ไม่มีแจ้งเตือนของฐานข้อมูล
12. **กลาง · ที่อยู่ที่ใช้นับการลองผิดยังไม่ได้ตรวจบน server จริง** (`api.ts:12` ใช้ X-Forwarded-For ตัวสุดท้าย) ถ้าเป็นที่อยู่ของ Cloudflare คนเดียวล็อกทุกคนได้ หรือปลอมได้
13. **กลาง · CSRF พึ่ง SameSite=Lax อย่างเดียว** บันทึกแบบ `text/plain` ข้ามเว็บผ่าน, login CSRF ได้ แก้: บังคับ JSON + ตรวจ Origin/Sec-Fetch-Site, cookie ชื่อ `__Host-`
14. **กลาง · ความลับและการเข้าถึงของทีมงาน** งานประจำของทีมงานต้องวาง doadmin ใน Console ของแอป ใครเข้า Console ได้เห็นรหัสทั้งหมด (`env`) ไม่มีขั้นตอนเปลี่ยนรหัสหรือเอาคนออก

## ตรวจแล้วดี

- แยกข้อมูลระหว่างร้าน: RLS บังคับทุกตาราง shop_id และ branch มาจาก session ลองข้ามร้านแล้วได้ 404/403 ทุกทาง · สาขา Franchise แยกกัน ช่องอัปเดตสดไม่รั่วข้ามสาขา

- หน้าทีมงาน: แอปยืนยันตัวตน 6 หลัก กันใช้ซ้ำ session ต่อแท็บ CSP เข้มงวด ไม่มี innerHTML ลงประวัติทุกการกระทำ

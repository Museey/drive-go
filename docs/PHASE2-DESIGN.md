## สรุปสำหรับเจ้าของโปรเจกต์

### เฟส 2 เปลี่ยนอะไร
- ข้อมูลของร้านไปอยู่ที่ server: เปิดจากเครื่องไหนก็เห็นข้อมูลชุดเดียวกัน
- ก่อนเข้าระบบ เบราว์เซอร์จะไม่ได้รับข้อมูลร้านเลย (ระบบเดิมโหลดข้อมูลทั้งร้าน รวมรหัสผ่านทุกบัญชี ตั้งแต่เปิดหน้า)
- รหัสผ่านตรวจที่ server เก็บแบบ hash และไม่ส่งไปที่เบราว์เซอร์ จึงไม่มีใครเห็นรหัสของคนอื่น (A3)
- หน้าจอ ปุ่ม และข้อความเหมือนเดิมทุกตัวอักษร ยกเว้นจุดที่อนุมัติให้เปลี่ยน (หัวข้อ 9)

### สิ่งที่เฟส 2 ยังไม่รองรับ: หลายคนในอู่เดียวกันทำงานพร้อมกัน
หน้าจอเดิมถือข้อมูลทั้งร้านไว้ในเครื่อง และไม่รู้ว่าคนอื่นเพิ่งบันทึกอะไร
ถ้าแคชเชียร์สองคนออกบิลในวันเดียวกัน ทั้งคู่จะขยับตัวนับเลขที่เอกสารตัวเดียวกัน
คนที่บันทึกทีหลังจึงถูกปฏิเสธตามข้อ P1 และต้องโหลดหน้าใหม่ ทั้งที่หน้าจออาจบอกไปแล้วว่าบันทึกสำเร็จ
ระบบจึงใช้ทดสอบได้ แต่ยังไม่พร้อมให้อู่ใช้จริง เรื่องนี้แก้ในเฟส 3 (ออกเลขที่เอกสารและตัดสต๊อกที่ server
และให้ทุกเครื่องในอู่เห็นการเปลี่ยนแปลงทันที) ซึ่งต้องเสร็จก่อนเปิดอู่นำร่องตามแผนเดิมอยู่แล้ว

## 1. ข้อเท็จจริงจากระบบเดิม

### 1.1 ที่เก็บข้อมูล
ระบบเดิมเก็บทุกอย่างใน IndexedDB ของเบราว์เซอร์ ฐานชื่อ `drivego-package-copy-v1-<แพ็กเกจ>` ช่อง `kv`
แต่ละช่องเป็นข้อความ JSON ทั้งก้อน (`STORE.get/set/del/keys`)

| key | คืออะไร | ใครเขียน |
|---|---|---|
| `garage.v22` | ข้อมูลร้าน (`DB`) ของ Biz/ProX และของสาขาแรกใน Franchise | `save()` |
| `garage.v22::<รหัสสาขา>` | ข้อมูลของสาขาอื่นใน Franchise (`brKey`) | `save()` หลัง `frLoadBranch` |
| `franchise.v22` | ข้อมูลเครือ (`FR`): สาขา บัญชี ใบขอเบิก คลังกลาง | `frSave()` |
| `dgb.v22` | บัญชีร้าน (`DGB`): รหัสร้าน ชื่อผู้ใช้และรหัสผ่านเจ้าของ วันทดลองใช้ และ session | `dgbSave()` |
| `garage.v22.bak.<วันที่>` | จุดสำรองอัตโนมัติวันละครั้ง (เก็บ 5 จุด) และที่กดสร้างเอง | `autoBackup`, เมนู 10 |
| `garage.v22.bak.before-restore`, `.bak.before-saleflow` | สำรองก่อนกู้คืน / ก่อนย้ายรูปแบบข้อมูล | กู้คืน, การย้ายข้อมูลของ pkgSaleFlow |
| `garage.v22.trialkeep`, `dgb.fresh.v22`, `dgb.guide.v22` | สำเนาข้อมูลทดลอง และค่าของหน้าทดลอง/หน้าแนะนำ | ฟีเจอร์ทดลอง |

localStorage ใช้แค่ค่าเล็ก ๆ ของเครื่อง เช่น `pkgAutoTrialDone`

### 1.2 ขนาดข้อมูล
| ชุดข้อมูล | `garage.v22` (UTF-8) | บีบอัด gzip | ก้อนใหญ่ที่สุด (สัดส่วนของ JSON) |
|---|---|---|---|
| พร้อมทดลอง (fixture) | 0.3 MB | — | พนักงาน 25% (สิทธิ์คนละราว 4,600 ตัวอักษร), ใบเสร็จ 10% |
| ข้อมูลตัวอย่าง 36 เดือน | **18.1 MB** | **1.2 MB** | ใบเสร็จ 2,055 ใบ 28%, ใบเสนอราคา 1,859 ใบ 26%, ใบตัดสต็อก 2,058 ใบ 25%, ความเคลื่อนไหวสต๊อก 9,991 รายการ 12% |

`DB` มี 40 กว่าช่อง แบ่งได้เป็น
- **รายการที่มี `id`** (ใบเสร็จ ลูกค้า สินค้า ฯลฯ 20 กว่าชุด) ในข้อมูลตัวอย่างมี `id` ซ้ำ 2 คู่ในความเคลื่อนไหวสต๊อก
  ซึ่งเป็นคนละรายการจริง (`uid()` สร้างจากเวลา + เลขสุ่ม 5 ตัว) จึงห้ามรวมเป็นแถวเดียว
- **ผังบัญชี `coa`** ไม่มี `id` แต่รหัสบัญชี `code` ไม่ซ้ำ
- **ก้อนที่มีรายการซ้อนข้างใน**: `px` (คิว การสอบถาม SOS คลังความรู้ ฯลฯ), `fifo` (`lots`, `allocs`)
- **ตารางค่า**: `seq` ตัวนับเลขที่เอกสาร (ข้อมูลตัวอย่างมี 3,617 ตัว), `paySlips`, `whtDocs`
- **ก้อนตั้งค่า**: `shop`, `map`, `custRule`, `venRule`, `regCols`, `qPresets`, `pkgSaleFlow`
- **ค่าเดี่ยว**: `curEmp`, `curBranch`, `stockCtx`, `branchV`, `pkgCutsV`, `docNoV`

ช่องใหม่ถูกเพิ่มระหว่างใช้งาน (`qPresets`, `transfers`, `fifo`) ระบบใหม่ต้องรับช่องที่ไม่รู้จักได้โดยไม่ทำข้อมูลหาย

เลขที่เอกสารไม่ซ้ำกันในแต่ละชุดเอกสาร (ใบเสร็จ ใบเสนอราคา ใบตัดสต็อก ฯลฯ) และเลขใบกำกับภาษี (`taxNo`) ไม่ซ้ำ
ทั้งในข้อมูลทดลองและข้อมูลตัวอย่าง 36 เดือน

- `dgb.v22` และ `franchise.v22` ถูกเขียนตอนเปิดโปรแกรมและทุกครั้งที่เข้า/ออกระบบ (176 และ 168 ครั้ง)

### 1.5 ข้อมูลของ "คนที่ใช้งานอยู่" ที่เก็บรวมกับข้อมูลร้าน
`DB.curEmp` (พนักงานที่เข้าระบบอยู่), `DGB.session.who`, `FR.session` (บัญชีที่เข้าระบบ และสาขาที่ HQ เข้าไปดู)
ระบบเดิมใช้ได้เพราะมีผู้ใช้ทีละคนต่อเบราว์เซอร์ ถ้าเก็บรวมไว้บน server คนที่เข้าระบบคนล่าสุดจะกลายเป็น "ผู้ใช้ปัจจุบัน" ของทุกคน
ส่วน `DB.curBranch` และ `DB.stockCtx` (คลังที่กำลังดูอยู่ใน Biz หลายสาขา) ทำให้ข้อมูลสต๊อกในเครื่องถูกสลับทั้งชุด
(`swapStock` ย้ายจำนวนของคลังที่ดูอยู่ไปไว้ช่องบนสุด และของคลังอื่นไปไว้ใน `bq`) หน้าตาของรายการสต๊อกที่บันทึกจึงขึ้นกับคนที่บันทึกล่าสุด

### 1.6 ทางเข้าระบบ
ทุกทางตรวจรหัสในเบราว์เซอร์กับข้อมูลที่โหลดมาทั้งหมด
1. เจ้าของร้าน Biz/ProX: ชื่อผู้ใช้ (`dg1688`) หรืออีเมล + `DGB.shop.pass`
2. พนักงาน Biz/ProX: เบอร์โทร + `emp.dgbPass` (เบอร์ซ้ำกับคนอื่นหรือซ้ำกับเจ้าของ ระบบปฏิเสธ)
3. Franchise HQ / หัวหน้าสาขา / พนักงานสาขาที่ออกบัญชีแล้ว: `FR.accounts` (ชื่อผู้ใช้ไม่สนตัวพิมพ์เล็กใหญ่)
4. Franchise แบบเก่า: `<ชื่อผู้ใช้หัวหน้าสาขา>.<รหัสพนักงาน>` + PIN (เช่น `b001.EMP001`)
5. ฟีเจอร์เดโม (A1 ตัดออก): เข้าเป็นเจ้าของ/HQ โดยไม่กรอกรหัส, "ทดสอบบัญชีอื่น", สลับผู้ใช้ด้วย PIN

ข้อความผิดพลาดของแต่ละกรณีต่างกัน (เช่น "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง", "รหัสนี้ถูกระงับการใช้งานโดย HQ — ติดต่อสำนักงานใหญ่",
"ข้อมูลเข้าสู่ระบบซ้ำกัน กรุณาให้ผู้ดูแลแก้ไขบัญชีก่อน") server ต้องให้ผลและข้อความเดียวกันทุกกรณี

### 1.7 Franchise

### 1.8 ProX โหมดออนไลน์
หน้าจอ ProX มีปุ่ม "เชื่อมต่อสาขา" ที่ต่อ server เครือตาม URL ที่ผู้ใช้กรอก (`/api/auth/login`, `/api/queue`, `/api/accept/:id`,
`/api/bill/:id`, `/api/pay/:id`, `/api/stock/report`, `/api/dc/products`, `/api/dc/requests` …) และดึงข้อมูลทุก 7 วินาที
server นี้ไม่อยู่ในไฟล์ที่ได้มา (S89 ทดสอบได้แค่กรณีเชื่อมไม่ได้) จึงเป็นคำถาม Q4

### 1.9 ระบบเดิมเตรียมที่เก็บข้อมูลภายนอกไว้แล้ว
`STORE` มีโหมด `host` ที่ใช้ `window.storage.get / set / delete / list` แทน IndexedDB (ปิดไว้ด้วย `if(false&&…)` บรรทัดเดียว)
พร้อมข้อความบนหน้าตั้งค่าสำหรับโหมดนี้ และการสำรองอัตโนมัติก็ทำงานในโหมดนี้ด้วย (`['host','idb'].includes(STORAGE_MODE)`)
เฟส 2 จึงใช้ช่องนี้: เขียน `window.storage` ที่คุยกับ server แล้วแก้ระบบเดิมแค่บรรทัดนั้น (หัวข้อ 4.1)

- **ประกอบกลับ** ต้องได้ข้อความ JSON เดิมทุกไบต์ รวมลำดับ key ของ object เพราะโค้ดเดิมวนอ่าน object ตามลำดับ key
  (`Object.keys`, `for…in`) จึงเก็บ `data` เป็น `json` (เก็บข้อความตามเดิม) ไม่ใช่ `jsonb` (ซึ่งเรียง key ใหม่)
  ลำดับรายการและค่าในตารางค่าเรียงตาม `pos` ส่วนลำดับช่องบนสุดและช่องของก้อนที่มีรายการซ้อน (`px`, `fifo`) เก็บเป็นแถว `__layout` ของแต่ละ key
  (T5 ทดสอบด้วยการแบ่งแล้วประกอบ fixture ทั้ง 3 แพ็กเกจและข้อมูล 36 เดือนให้ตรงทุกไบต์)
- **ความลับ** ฝั่งเบราว์เซอร์เห็นเป็นค่าแทน (เช่น `********` ถ้าตั้งรหัสแล้ว, `''` ถ้ายังไม่ตั้ง)
  โค้ดเดิมที่ดูแค่ว่า "มีรหัสหรือยัง" (`!e.pin`, `e.dgbPass&&…`) จึงทำงานเหมือนเดิม
  ถ้าผู้ใช้พิมพ์รหัสใหม่ `window.storage` จะแยกค่านั้นออกจากรายการ ส่งไปเป็นคำขอตั้งรหัสใน transaction เดียวกัน แล้ว server เก็บเป็น hash
- **คลังที่กำลังดู** (`curBranch`, `stockCtx`) เฟส 2 ยังเก็บรวมกับข้อมูลร้านเหมือนเดิม การแยกเป็นของแต่ละคนทำในเฟส 3 พร้อมการตัดสต๊อกที่ server

### 3.3 ลำดับรายการ
รายการใหม่ได้ `pos` ต่อท้ายจาก server (มากกว่าตัวสุดท้ายเสมอ) ประกอบกลับเรียงตาม `pos` แล้ว `key`
จากการดักทั้ง 84 สถานการณ์ ระบบเดิมเพิ่มรายการที่ท้ายอย่างเดียว (หัวข้อ 1.3) ถ้า `window.storage` เจอลำดับแบบอื่น
(แทรกกลาง ใส่หน้าสุด เรียงใหม่) ให้ส่งลำดับทั้งชุดของหน่วยนั้นไปด้วย ซึ่งไม่ควรเกิด และ log ไว้ทุกครั้ง

### 3.4 เลขที่เอกสารห้ามซ้ำ (P2)
unique index บน (`shop_id`, `branch_id`, `unit`, `data->>'no'`) ของชุดเอกสาร (ใบเสร็จ ใบเสนอราคา ใบตัดสต็อก ใบรับสินค้า
รายจ่าย สินทรัพย์ ใบเคลม ใบแจ้งหนี้ ใบวางบิล ใบเบิก ใบตรวจนับ ใบเตือน ใบโอน) และบน `receipts.taxNo`
ใช้ `branch_id` ในดัชนีด้วย เพราะใน Franchise แต่ละสาขามีตัวนับของตัวเอง (ฐานข้อมูลสาขาใหม่เริ่มจาก `seq` ว่าง) เลขจึงอาจซ้ำข้ามสาขาได้
(ข้อ A7 เปลี่ยนเลขที่เอกสารให้มีรหัสสาขาในเฟส 3) ถ้าบันทึกชน ดัชนี server ตอบเหมือนการชนตาม P1

### 3.5 Row-Level Security
- server ต่อฐานข้อมูลด้วย role ที่ไม่มีสิทธิ์ข้าม RLS และทุกคำขอทำใน transaction:
  `select set_config('app.shop_id', $1, true), set_config('app.branch_scope', $2, true)` (เทียบเท่า `SET LOCAL`) ค่ามาจาก session เท่านั้น
- policy ของทุกตารางของอู่: `shop_id = current_setting('app.shop_id')::uuid` ทั้งอ่านและเขียน
  ถ้าลืมตั้งค่า `current_setting` จะ error ทำให้ล้มแบบปิด ไม่ใช่เห็นข้อมูลทุกร้าน
- policy แบบ restrictive ของสาขา: `app.branch_scope = '*'` (HQ) เห็นทุกสาขา, ผู้ใช้สาขาเห็นสาขาตัวเองและข้อมูลระดับเครือ (`branch_id = ''`)
- `shops` และ `sessions` ใช้ก่อนรู้ว่าเป็นร้านไหน จึงเข้าผ่านฟังก์ชัน `security definer` สองตัว (หาร้านจากรหัส, หา session จาก hash ของ token) เท่านั้น
- T3 เขียน test ก่อน: ตั้งเป็นร้าน A แล้วอ่าน/เขียน/ลบแถวของร้าน B ต้องไม่ได้, ไม่ตั้งค่าต้อง error, ผู้ใช้สาขา B001 อ่านของ B002 ไม่ได้

## 4. การรับส่งข้อมูล

### 4.1 `window.storage` (ไฟล์ใหม่ `frontend/js/00-server-storage.js`)
เขียนเป็น TypeScript ใน `server/lib/` แล้ว build เป็นไฟล์เดียวที่โหลดก่อน `js/03.js`
และแก้ `js/03.js` บรรทัดเดียว: เอา `false&&` ออกจาก `STORE.init` เพื่อเปิดโหมด `host`

| คำสั่ง | ทำอะไร |
|---|---|
| `get(key)` ของข้อมูลหลัก | ครั้งแรกขอจาก server (`GET /api/storage/<key>`) แล้วเก็บสำเนาไว้ ครั้งต่อไปตอบจากสำเนา (`save()` อ่านค่าเดิมทุกครั้งเพื่อทำจุดสำรอง) |
| `set(key, json)` ของข้อมูลหลัก | แบ่งเป็นหน่วย เทียบกับสำเนาที่ server ยืนยันแล้ว ส่งเฉพาะหน่วยที่เปลี่ยน (`POST /api/storage/<key>/changes`) ไม่มีอะไรเปลี่ยนก็ไม่ส่ง |
| `set` ของจุดสำรอง (`.bak.*`) | ขอให้ server ทำจุดสำรองจากข้อมูลของตัวเอง ไม่อัปโหลดข้อมูลทั้งก้อน |
| `get/set/delete` ของ key อื่น | เก็บเป็น `blobs` ตรง ๆ |
| `list()` | key ทั้งหมดของร้าน/สาขานั้น (ให้เหมือน IndexedDB ที่ `keys()` คืนทุก key) |

- ส่งทีละคำขอตามลำดับ (คำขอถัดไปรอคำขอก่อนเสร็จ) เพราะ `save()` ของระบบเดิมถูกเรียกต่อกันหลายครั้งโดยไม่รอ
- `set` ต้องไม่ throw: โหมด `host` ของระบบเดิมถ้า `set` ล้มจะไปเขียน localStorage แทนเงียบ ๆ ซึ่งผิดในระบบใหม่
  การล้มทุกแบบจัดการใน `window.storage` เอง (หัวข้อ 4.4)
- ความเร็ว: ระบบเดิม `JSON.stringify` ข้อมูลทั้งก้อนทุกครั้งที่บันทึกอยู่แล้ว การแบ่งหน่วยเพิ่มงานอีกราวเท่าตัว
  T6 วัดกับข้อมูล 36 เดือน ถ้าช้าเกินให้ใช้วัตถุ `DB` ตรง ๆ แทนการ parse ข้อความ

### 4.2 API
| คำขอ | ทำอะไร |
|---|---|
| `POST /api/auth/login` `{user, pass}` | ตรวจรหัส สร้าง session ตั้ง cookie `HttpOnly; Secure; SameSite=Lax` คืนข้อผิดพลาดเป็นข้อความเดียวกับระบบเดิม |
| `POST /api/auth/logout` | ปิด session |
| `POST /api/auth/password` | เปลี่ยนรหัสของตัวเอง (ต้องใส่รหัสเดิม) |
| `GET /api/storage` | รายชื่อ key (`list`) |
| `GET /api/storage/<key>` | ข้อมูลหลักที่ประกอบแล้ว (ไม่มีความลับ, ช่องของ session มาจาก session) หรือจุดสำรอง หรือ blob |
| `POST /api/storage/<key>/changes` | `{base: {หน่วย: version}, upsert: […], delete: […], order: […], secrets: […]}` ทำใน transaction เดียว คืน version ใหม่ หรือ 409 พร้อมรายการที่ชน |
| `PUT / DELETE /api/storage/<key>` | blob และจุดสำรอง |

การตั้ง/ระงับบัญชีพนักงานและบัญชีเครือในระบบเดิมคือการแก้รายการ `emp` / `FR.accounts` แล้วบันทึก
server จึงอัปเดต `users` จากรายการเหล่านั้นใน transaction เดียวกับการบันทึก (เบอร์เข้าระบบ, ชื่อผู้ใช้, เปิด/ระงับ, บทบาท, สาขา)

### 4.3 การชนกัน (P1)
- `window.storage` ส่ง version ที่ตัวเองเห็นของทุกหน่วยที่เปลี่ยน server ล็อกแถวเหล่านั้น (`select … for update`) แล้วเทียบ
  ถ้ามีหน่วยไหน version ไม่ตรง หรือเลขที่เอกสารชนดัชนี ปฏิเสธทั้งคำขอ (ไม่บันทึกครึ่ง ๆ)
- รายการใหม่ (เพิ่ม) ไม่ชนกับใคร ยกเว้น key หรือเลขที่เอกสารซ้ำ
- การชนที่จะเกิดบ่อยเมื่อหลายคนใช้พร้อมกัน: ตัวนับ `seq` ของเอกสารชนิดเดียวกันในเดือนเดียวกัน, `pkgSaleFlow.used`
  (ตัวนับที่เพิ่มทุกครั้งที่ขาย), จำนวนสต๊อกของสินค้าตัวเดียวกัน, ล็อต FIFO และการโอนสินค้าระหว่างคลังที่แก้สต๊อกทุกรายการ
  — จึงต้องแก้ในเฟส 3 ก่อนใช้จริง

### 4.5 จุดสำรองและการกู้คืน
ทำงานเหมือนเดิม (S74): จุดสำรองอัตโนมัติวันละครั้งตอนบันทึกครั้งแรกของวัน เก็บ 5 จุด กดสร้างเองได้ กู้คืนได้
- ชื่อจุดสำรองมาจากวันที่ที่ระบบเดิมส่งมาใน key (`garage.v22.bak.2026-10-13`) ไม่ใช้นาฬิกาของ server ผลจึงตรงเฉลย
- server เก็บข้อมูลทั้งก้อนแบบ gzip ในตาราง `backups` (ข้อมูลตัวอย่าง 3 ปีเหลือ 1.2 MB ต่อจุด)
  ย้ายไป object storage ได้ภายหลังโดยไม่กระทบหน้าจอ
- การกู้คืน / ล้างข้อมูล / นำเข้าไฟล์ / โหลดข้อมูลตัวอย่าง เปลี่ยนข้อมูลทั้งก้อน ใช้ทางเดียวกับการบันทึกปกติ (คำขอใหญ่ครั้งเดียว ใน transaction เดียว)
- นอกจากนี้ผู้ให้บริการฐานข้อมูลต้องสำรองแบบย้อนเวลาได้ (point-in-time) ซึ่งเป็นคนละเรื่องกับจุดสำรองบนหน้าจอ

### 4.6 ก่อนเข้าระบบ
ก่อนมี session `GET /api/storage/<key>` คืนเฉพาะค่าที่หน้าเข้าระบบต้องใช้ (เช่น ชื่อร้าน, เครือเปิดโหมดแฟรนไชส์อยู่หรือไม่)
ไม่มีข้อมูลร้าน รายชื่อบัญชี หรือรหัสผ่าน (T7 ไล่ว่าหน้าเข้าระบบอ่านช่องไหนบ้าง)
และระบบเดิมที่เจอข้อมูลว่างจะสร้างข้อมูลตัวอย่าง 36 เดือนเอง (`seedDemo36`) ซึ่งเป็นฟีเจอร์เดโมตาม A1
จึงต้องแก้บรรทัดนั้นให้เริ่มระบบตามปกติแทน (หัวข้อ 9) หลังเข้าระบบสำเร็จ หน้าจอโหลดข้อมูลจริงแล้วเริ่มระบบใหม่ในที่
แบบเดียวกับที่ `frLoadBranch` ของระบบเดิมทำตอนสลับสาขา จากนั้นทำขั้นตอนหลังเข้าระบบของระบบเดิมต่อ

## 8. การทดสอบ (T9)

### 8.1 ตัวขับระบบใหม่ `TARGET=new`
- เปิด server ของตัวเองบนพอร์ตสุ่ม + ฐานข้อมูลของการรันนั้น (Docker) แบบเดียวกับ `LEGACY_PORT`
- ทุก test สร้างร้านใหม่จาก fixture เดิม (`tests/fixtures/*.json`) ด้วยโค้ดเดียวกับสคริปต์เปิดอู่ (P3) ร้านละ test ไม่ปนกัน
- ใช้สถานการณ์และเฉลยชุดเดิมทั้งหมด
- จบทุกสถานการณ์ด้วยการโหลดหน้าใหม่ แล้วเทียบข้อมูลก่อนและหลังโหลด (ยกเว้นช่องของ session)
  พิสูจน์ว่าทุกอย่างบันทึกถึง server จริง ไม่ได้ค้างอยู่แค่ในเบราว์เซอร์
- ระหว่างรัน server ต้องไม่ปฏิเสธการบันทึกเลย (สถานการณ์มีผู้ใช้คนเดียว) ถ้ามีถือว่าไม่ผ่าน

### 8.2 พฤติกรรมที่ตั้งใจเปลี่ยน
- สถานการณ์ใหม่ของพฤติกรรมที่เปลี่ยน เขียนเป็นการตรวจตรง ๆ (`expect`) เพราะเฉลยบันทึกได้จากระบบเดิมเท่านั้น
- ไฟล์ `tests/intentional-changes.json` บอกว่าสถานการณ์เดิมเรื่องไหน (หรือขั้นไหน) ถูกแทนด้วยสถานการณ์ใหม่เรื่องไหน ตามข้อตัดสินข้อไหน
  `TARGET=new` ไม่รันเฉพาะส่วนที่อยู่ในไฟล์นี้ และต้องล้มถ้าสถานการณ์ที่มาแทนไม่มีอยู่จริง
- Q7: ถ้าอนุมัติ กรรมการข้อมูลบันทึกช่องความลับเป็น "มีรหัส / ว่าง" (ต้องบันทึกเฉลยของ 7 เรื่องที่มีรหัสในข้อมูลใหม่จากระบบเดิม)
  สถานการณ์อย่าง S41, S44, S47, S59 จึงยังใช้ตรวจระบบใหม่ได้ เหลือแทนเฉพาะขั้นที่หน้าจอแสดงตัวรหัส

### 8.3 test ใหม่ที่ไม่ใช่สถานการณ์หน้าจอ
- แยกข้อมูลระหว่างอู่และระหว่างสาขา (T3, T8)
- แบ่งแล้วประกอบข้อมูลทั้ง 4 ชุดได้ตรงทุกไบต์ (T5)
- สองเบราว์เซอร์บันทึกรายการเดียวกัน คนหลังได้ข้อความชนกัน (P1) และเลขที่เอกสารซ้ำถูกปฏิเสธ (P2)

## 10. ย้ายไปเฟส 3 (บันทึกไว้ไม่ให้ลืม)
- ทุกเครื่องในอู่เห็นการเปลี่ยนแปลงของคนอื่นทันที (server ส่งให้ทาง SSE แล้วหน้าจอดึงเฉพาะส่วนที่เปลี่ยน) — **เสนอเพิ่มเข้าแผนเฟส 3 (Q8)**
- ออกเลขที่เอกสาร ตัดสต๊อก/FIFO และนับ `pkgSaleFlow.used` ที่ server (หมดปัญหาการชนที่พบบ่อยในหัวข้อ 4.3)
- คลังที่กำลังดู (`curBranch`, `stockCtx`) เป็นของแต่ละคน
- สิทธิ์ละเอียดตาม `emp.perms` ที่ server
- ไฟล์แนบใน `px.learn` และรูปสินค้าย้ายไป object storage

## 11. ความเสี่ยงและสิ่งที่ต้องวัด
| เรื่อง | วิธีจัดการ |
|---|---|
| โหลดข้อมูลทั้งก้อนทุกครั้งที่เข้าระบบ (18 MB สำหรับข้อมูล 3 ปี) | ส่งแบบบีบอัด (ข้อมูลตัวอย่างเหลือ 1.2 MB) วัดใน T6 การโหลดทีละหน้าเป็นงานเฟส 4 |
| บันทึกช้าลงกับข้อมูลใหญ่ | วัดใน T6 กับข้อมูล 36 เดือน (หัวข้อ 4.1) |
| ขนาดฐานข้อมูล | ราว 6 MB ต่ออู่ต่อปีตามความหนาแน่นของข้อมูลตัวอย่าง 3,000 อู่ราว 18 GB ต่อปี + จุดสำรอง 5 จุดต่ออู่ราว 6 MB |
| `uid()` ของเบราว์เซอร์ชนกันได้ (พบในข้อมูลตัวอย่าง) | key ซ้ำใช้ `#2` ในรายการเดิม ส่วนรายการใหม่ที่ id ชนกับของคนอื่น server ปฏิเสธเหมือนชนกัน |
| ระบบเดิมเปลี่ยนรูปแบบข้อมูลเองระหว่างใช้งาน (migration ใน `boot`) | ช่องที่ไม่รู้จักเป็น "ก้อน" เสมอ และ log ไว้ |

## 12. โครงสร้างโฟลเดอร์ที่จะเพิ่ม
```
server/                 แอป Next.js + TypeScript
  app/api/…             route (ทางเข้าเท่านั้น)
  lib/units.ts          ตารางแบ่งข้อมูล (ใช้ร่วมกับ window.storage)
  lib/storage/…         แบ่ง/ประกอบ, บันทึก, จุดสำรอง
  lib/auth/…            เข้าระบบ, session, hash
  lib/db.ts             ต่อฐานข้อมูล + transaction ที่ตั้ง app.shop_id เสมอ
  db/migrations/*.sql   ตาราง + RLS
  client/storage.ts     ต้นฉบับของ frontend/js/00-server-storage.js
tools/new-shop.mjs      เปิดอู่ใหม่ / นำเข้า fixture (P3)
docker-compose.yml      PostgreSQL สำหรับเครื่องนักพัฒนาและการรัน test
frontend/CHANGES.md     ทุกจุดที่แก้ในโค้ดเดิม พร้อมเหตุผล
```
